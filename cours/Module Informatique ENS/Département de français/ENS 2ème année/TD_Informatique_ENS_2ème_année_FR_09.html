Exercice 1 — Définir le cahier des charges (20 min)

Énoncé : Vous devez développer une application de gestion des notes pour votre département. Rédiger les sections suivantes du cahier des charges :

  1. Contexte et objectifs (2-3 phrases)
  2. Utilisateurs cibles (qui utilise l'app ?)
  3. Fonctionnalités essentielles (5 minimum)
  4. Contraintes techniques (langage, base de données, plateforme)

Corrigé :

CAHIER DES CHARGES — Gestion des Notes ENS

1. Contexte et objectifs
   Le département de français de l'ENS Mostaganem souhaite
   informatiser le suivi des notes des étudiants pour les modules
   d'informatique. L'objectif est de remplacer les tableurs Excel
   par une application centrale.

2. Utilisateurs cibles
   - Admin : gestion des utilisateurs, des matières, des semestres
   - Enseignant : saisie des notes, consultation des moyennes
   - Étudiant (lecture seule) : consultation de son relevé

3. Fonctionnalités essentielles
   - Authentification (login/mot de passe)
   - CRUD étudiants, enseignants, matières
   - Saisie des notes avec coefficient
   - Calcul automatique des moyennes (par matière, semestre)
   - Génération de relevé PDF
   - Export CSV

4. Contraintes techniques
   - Langage : Python (Django) ou Java (Spring Boot)
   - Base : PostgreSQL ou MySQL
   - Interface : Web responsive (Bootstrap)
   - Déploiement : serveur ENS ou cloud (Hébergement institutionnel)

Exercice 3 — Architecture et routes (15 min)

Énoncé : Pour l'application web, définir :

  1. L'architecture technique (3-tiers)
  2. Les routes API REST (méthode + URL)
  3. Les vues/templates minimaux

Corrigé :

1. Architecture 3-tiers :

[Client Navigateur]
       ↕ HTTP / HTTPS
[Backend Django / Spring]
       ↕ JDBC / ORM
[Base de données PostgreSQL]

2. Routes API REST :

Méthode URL Fonction
POST /api/login Authentification
GET /api/etudiants Liste étudiants
GET /api/etudiants/{id} Détail étudiant
POST /api/etudiants Créer étudiant
GET /api/matieres Liste matières
GET /api/matieres/{id}/moyenne Moyenne matière
POST /api/notes Saisir note
GET /api/etudiants/{id}/releve Relevé PDF
GET /api/export/csv Export CSV

3. Vues minimales : - Page de connexion (login.html) - Dashboard enseignant (dashboard.html) - Saisie de notes (saisie_notes.html) - Relevé étudiant (releve.html) - Administration (admin.html)

Exercice 5 — Plan de développement (jalons) (15 min)

Énoncé : Établir un plan de développement sur 6 semaines pour l'application. Définir 3 sprints de 2 semaines avec les livrables de chaque sprint.

Corrigé :

PLAN DE DÉVELOPPEMENT — Sprint 0 à 3

SPRINT 0 (Semaine 1-2) — Fondations
  J1-3 : Installation environnement (Django/Spring + PostgreSQL)
  J4-7 : Modèle de données (classes entité)
  J8-10 : Authentification + pages statiques
  ✅ Livrable : App avec login + navbar

SPRINT 1 (Semaine 3-4) — Fonctions principales
  J11-13 : CRUD étudiants, enseignants, matières
  J14-16 : Saisie des notes avec coefficients
  J17-18 : Calcul automatique des moyennes
  ✅ Livrable : Saisie et consultation des notes

SPRINT 2 (Semaine 5-6) — Finalisation
  J19-20 : Relevé de notes PDF
  J21-22 : Export CSV
  J23-24 : Tests utilisateurs + corrections
  J25-26 : Déploiement + documentation
  ✅ Livrable : App livrée + formée

RÉPARTITION :
- Modèle et back-end : 60 %
- Front-end et UI : 25 %
- Tests et déploiement : 15 %

Grille d'évaluation

Critère Poids Non acquis (0) Partiel (0.5) Acquis (1)
Cahier des charges 20 % Sections manquantes ou vagues Partiellement rédigé Complet, clair et structuré
Diagramme de classes UML 20 % Absent ou erroné Classes identifiées sans relations Classes + héritage + multiplicités corrects
Architecture et routes API 20 % Architecture non définie Routes partielles Architecture 3-tiers + routes REST complètes
Maquette wireframe 20 % Absente ou illisible Ébauche de maquette Wireframe détaillé et cohérent
Plan de développement (sprints) 20 % Aucun plan Jalons partiels 3 sprints avec livrables concrets

Note pédagogique ENS

Transposition didactique : La conception d'un cahier des charges et la modélisation UML peuvent être transposées au lycée sous forme de projet fil rouge. Les élèves apprennent à structurer une pensée algorithmique et à anticiper les besoins utilisateurs avant de coder.

Conseil pour l'enseignant formateur : Insister sur l'importance de la phase de conception avant le développement. Faire travailler les étudiants en binômes sur des cas concrets (ex. application scolaire) pour rendre l'exercice authentique.

Prolongement : Proposer un mini-projet complet où les étudiants réalisent le diagramme de classes, implémentent le backend et présentent leur travail lors d'une soutenance.
