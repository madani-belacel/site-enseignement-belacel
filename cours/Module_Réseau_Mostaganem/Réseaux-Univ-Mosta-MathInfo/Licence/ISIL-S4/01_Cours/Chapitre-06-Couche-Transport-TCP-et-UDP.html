  5. Identifier les ports well-known des services courants.

1. Rôle de la couche Transport

La couche Transport (Layer 4) assure la communication de bout en bout (entre processus/applications sur des hôtes distants) :

Fonction Description
Multiplexage/démultiplage Diriger les données vers la bonne application (via les ports)
Fiabilité (TCP) Retransmission, ordonnancement, contrôle d'erreurs
Contrôle de flux Adapter le débit à la capacité du récepteur
Segmentation Découper les messages en segments

La couche Réseau (IP) livre des paquets hôte à hôte. La couche Transport livre des données processus à processus.

2. Ports et sockets

2.1 Port

  • Numéro sur 16 bits → plage 0–65535.
  • Identifie un processus/application sur un hôte.
Plage Type Exemples
0 – 1023 Well-known (système) 80 (HTTP), 443 (HTTPS), 53 (DNS), 22 (SSH)
1024 – 49151 Registered 3306 (MySQL), 8080 (HTTP alt)
49152 – 65535 Dynamiques/éphémères Ports clients temporaires

2.2 Socket

Une socket = adresse IP + port → identifie de manière unique une connexion :

$$\text{Socket} = (\text{IP}, \text{Port})$$

Exemple : (192.168.1.10, 54321) — processus client sur le PC.

Une connexion TCP est identifiée par un quadruplet : $$(IP_{src}, Port_{src}, IP_{dest}, Port_{dest})$$

2.3 Ports well-known essentiels

Port Protocole Service
20/21 TCP FTP (data/control)
22 TCP SSH
23 TCP Telnet
25 TCP SMTP (email)
53 TCP/UDP DNS
67/68 UDP DHCP
80 TCP HTTP
110 TCP POP3
443 TCP HTTPS
3389 TCP RDP (Bureau à distance)

3. Protocole UDP

UDP (User Datagram Protocol) — RFC 768

3.1 Caractéristiques

Propriété Valeur
Mode Sans connexion (connectionless)
Fiabilité Non fiable (pas de retransmission)
Ordre Non garanti
Overhead Minimal (8 octets d'en-tête)
Vitesse Rapide

3.2 Format du datagramme UDP

┌────────────────┬────────────────┬──────────┬──────────┐
│  Port Source   │  Port Dest     │ Longueur │ Checksum │
│   (16 bits)    │   (16 bits)    │(16 bits) │(16 bits) │
├────────────────┴────────────────┴──────────┴──────────┤
│                      Données (Payload)                 │
└───────────────────────────────────────────────────────┘

3.3 Usages de UDP

Application Raison du choix UDP
DNS Requête/réponse simple, petite taille
DHCP Broadcast, pas de connexion
VoIP / Streaming Tolérance à la perte, faible latence
SNMP Requêtes de gestion réseau
Online gaming Rapidité > fiabilité absolue

4. Protocole TCP

TCP (Transmission Control Protocol) — RFC 793

4.1 Caractéristiques

Propriété Valeur
Mode Orienté connexion (connection-oriented)
Fiabilité Fiable (retransmission, ACK)
Ordre Garanti (numéros de séquence)
Contrôle de flux Fenêtre glissante (flow control)
Overhead Plus élevé (20+ octets d'en-tête)

4.2 Format du segment TCP

┌──────────┬──────────┬─────────────────┬─────────────────┐
│ Port Src │ Port Dst│  Sequence Number (32 bits)         │
├──────────┴──────────┼─────────────────┬─────────────────┤
│   Ack Number (32)   │Offset│ Flags  │    Window Size   │
├─────────────────────┼──────┴────────┼───────────────────┤
│      Checksum       │  Urgent Ptr  │    Options         │
├─────────────────────┴──────────────┴───────────────────┤
│                      Données (Payload)                  │
└────────────────────────────────────────────────────────┘
Champ Rôle
Sequence Number Numéro du 1er octet de données du segment
Ack Number Prochain octet attendu (accusé de réception)
Flags SYN, ACK, FIN, RST, PSH, URG
Window Size Taille de la fenêtre de réception (flow control)

4.3 Three-Way Handshake (établissement de connexion)

Client                              Serveur
  │                                    │
  │──────── SYN (seq=x) ──────────────→│  1. Client demande connexion
  │                                    │
  │←─── SYN+ACK (seq=y, ack=x+1) ─────│  2. Serveur accepte
  │                                    │
  │──────── ACK (ack=y+1) ────────────→│  3. Client confirme
  │                                    │
  │        Connexion ÉTABLIE           │
  │←────────── Data ─────────────────→│  Échange de données
  │                                    │
  │──────── FIN ──────────────────────→│  Fermeture
  │←─────── FIN+ACK ──────────────────│
  │──────── ACK ──────────────────────→│
  │        Connexion FERMÉE            │

sequenceDiagram
    participant C as Client
    participant S as Serveur
    C->>S: SYN (seq=100)
    S->>C: SYN-ACK (seq=300, ack=101)
    C->>S: ACK (ack=301)
    Note over C,S: Connexion établie
    C->>S: DATA
    S->>C: DATA + ACK
    C->>S: FIN
    S->>C: FIN + ACK
    C->>S: ACK
    Note over C,S: Connexion fermée

4.4 Fermeture de connexion (Four-Way)

  1. Client → FIN → Serveur
  2. Serveur → ACK → Client (half-close)
  3. Serveur → FIN → Client
  4. Client → ACK → Serveur

4.5 Contrôle de flux (Flow Control)

  • Le récepteur annonce sa fenêtre de réception (Window Size).
  • L'émetteur ne peut pas envoyer plus de données que la fenêtre le permet.
  • Évite la saturation du buffer du récepteur.

4.6 Contrôle de congestion (aperçu)

  • TCP adapte son débit en fonction de la congestion du réseau.
  • Algorithmes : Slow Start, Congestion Avoidance (AIMD).
  • → Approfondi en SI-S5 / Ingénieur.

5. Comparaison TCP vs UDP

Critère TCP UDP
Connexion Orienté connexion (handshake) Sans connexion
Fiabilité ✅ Retransmission, ACK ❌ Best effort
Ordre ✅ Garanti ❌ Non garanti
Vitesse Plus lent (overhead) Plus rapide
En-tête 20–60 octets 8 octets
Contrôle de flux ✅ Fenêtre glissante ❌
Usage typique Web, email, FTP, SSH DNS, VoIP, streaming, jeux
Analogie Téléphone (appel avant de parler) Lettre (envoyer sans confirmation)

Règle pratique : Si la fiabilité est critique → TCP. Si la rapidité/latence est critique → UDP.

6. Multiplexage et démultiplexage

6.1 Multiplexage (émission)

Le transport collecte les données de plusieurs sockets et les transmet via IP :

App HTTP (port 80)  ──┐
App DNS  (port 53)  ──┼──→ TCP/UDP ──→ IP ──→ Réseau
App SSH  (port 22)  ──┘

6.2 Démultipliplexage (réception)

À la réception, TCP/UDP utilise le port destination pour livrer les données à la bonne application :

Réseau ──→ IP ──→ TCP/UDP ──→ Port 80 → Navigateur
                           ──→ Port 53 → Résolveur DNS

7. Exemples concrets

Exemple 1 — Connexion à un site web

  1. Navigateur ouvre socket (IP_client, port_ephemere) → (IP_serveur, 443)
  2. TCP three-way handshake
  3. TLS négocie le chiffrement (couche Présentation)
  4. HTTP GET envoyé via TCP
  5. Serveur répond avec HTML
  6. TCP ferme la connexion

Exemple 2 — Requête DNS (UDP)

  1. (192.168.1.10, 52341) → (8.8.8.8, 53) — datagramme UDP
  2. Serveur DNS répond en UDP — (8.8.8.8, 53) → (192.168.1.10, 52341)
  3. Pas de handshake, pas de retransmission TCP

Exemple 3 — Visualisation avec netstat

netstat -an          # Windows/Linux — connexions actives
netstat -tulnp       # Linux — ports en écoute

Sortie typique :

Proto  Local Address       Foreign Address     State
TCP    192.168.1.10:54321  142.250.80.68:443   ESTABLISHED
UDP    0.0.0.0:53                             
TCP    0.0.0.0:80          0.0.0.0:0           LISTENING
