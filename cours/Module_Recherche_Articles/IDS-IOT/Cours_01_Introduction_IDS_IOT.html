Introduction à la détection d'intrusion pour IoT

Cours 01 — Module IDS-IOT / RPL-ClusterIDS
  • Auteur : Dr. Madani BELACEL
  • Durée : 2 séances
  • Objectif : Comprendre pourquoi les réseaux IoT RPL ont besoin d'un IDS distribué
Objectif pédagogique : Identifier les vulnérabilités des réseaux IoT RPL, comprendre les limites des IDS centralisés, distinguer les approches DIDS, situer RPL-ClusterIDS dans la recherche.

1. Contexte : sécurité des réseaux IoT

Les réseaux de capteurs sans fil (WSN) et l'Internet des Objets (IoT) sont vulnérables à de nombreuses attaques en raison de leurs ressources limitées (énergie, mémoire, calcul), de leur nature sans fil et de leur déploiement souvent non surveillé. Le protocole de routage RPL (RFC 6550) est largement utilisé dans ces réseaux mais n'intègre aucun mécanisme de sécurité natif contre les nœuds malveillants internes.

1.1 Contraintes des nœuds IoT

  • Énergie : batteries limitées (typ. 2 AA pour Zolertia RE-Mote), pas de recharge
  • Mémoire : RAM 32-64 Ko, Flash 256-512 Ko
  • CPU : ARM Cortex-M3 32 MHz, pas de FPU matériel
  • Bande passante : IEEE 802.15.4 à 250 kbps, MTU 127 octets

1.2 Cinq attaques RPL simulées

  • Rank Attack : nœud malveillant annonce un rang artificiellement bas pour attirer le trafic. Signal : 75-85.
  • Selective Forwarding : nœud droppe sélectivement certains paquets. Plus agressif sur trafic C3 (65-75) que C0-C2 (35-45).
  • DAO Flood : inondation de messages DAO pour épuiser la mémoire du routeur frontalier. Signal : 60-70.
  • Wormhole : deux nœuds collusoires tunnelent le trafic hors bande. Signal 70-80 avec 25% de silence.
  • Mixed Attack : combinaison des quatre types simultanément.

2. Limites des IDS centralisés

  • Point de défaillance unique : si le nœud central est compromis, tout le système est paralysé
  • Congestion du réseau : tous les nœuds envoient leurs données vers un point central
  • Latence de détection : le temps de transmission retarde la réaction
  • Consommation d'énergie : transmissions longue distance épuisent les batteries
  • Non passage à l'échelle : difficile au-delà de 50 nœuds

3. Approche IDS distribuée (DIDS)

Un IDS distribué (DIDS) répartit la charge de détection sur l'ensemble du réseau.

  • Résilience (pas de point unique)
  • Réduction du trafic de signalisation
  • Détection plus rapide (traitement local)
  • Meilleure efficacité énergétique
  • Passage à l'échelle facilité

4. Contributions de RPL-ClusterIDS

  1. Clustering adaptatif : fonction d'affinité = topologie×3 + énergie×2 + trafic×1. Re-clustering tous les 120 ticks si score > 70.
  2. Élection de CH : fitness = NRE×2 + (100 - ETX×5). Rotation basée sur seuil 140+(id%8)×12+(id/8)×4.
  3. Détection à deux niveaux : règles R1-R4 avec EWMA, LAS = (R1×3+R2×2+R3+R4)/4. Seuil LAS > 50.
  4. Politiques contextuelles : Full (0x0F), Balanced (0x07), Eco (0x03).
  5. Pipeline reproductible : de Cooja aux figures LaTeX/TikZ.

5. Architecture à deux niveaux

  • Niveau 1 — Membre : ids_member_tick() avec masque de règles, LAS via EWMA. Si LAS > 50, alarme.
  • Niveau 2 — CH : reçoit LAS et alarme. Si alarme ET LAS > 50, attaque confirmée.
  • Variants : B1 (border router only), B2 (flat), B3 (centralisé), MAIN (complet), ablations.
