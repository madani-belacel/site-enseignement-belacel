Architecture distribuée de RPL-ClusterIDS

Cours 02 — Module IDS-IOT / RPL-ClusterIDS
  • Auteur : Dr. Madani BELACEL
  • Durée : 2 séances
  • Objectif : Comprendre l'architecture à deux niveaux du système DIDS

1. Vue d'ensemble de l'architecture

RPL-ClusterIDS adopte une architecture hiérarchique à deux niveaux qui répartit les responsabilités de détection entre les nœuds membres et les Cluster Heads (CH). Cette séparation permet d'équilibrer la charge de calcul et de communication tout en maintenant une détection efficace.

Les composants logiciels sont organisés en modules C dans le répertoire code_source_RPL_ClusterIDS/ :

  • clusterids-node.c — Point d'entrée : trafic UDP (classes C0-C3), racine RPL, orchestration de la couche IDS
  • clus_form.c / .h — Formation des clusters et fonction d'affinité
  • ch_elect.c / .h — Élection des Cluster Heads et rotation
  • ids_member.c / .h — Détection locale (règles R1-R4) et calcul LAS
  • ids_ch.c / .h — Agrégation des LAS au niveau CH
  • ctx_policy.c / .h — Politiques contextuelles Full/Balanced/Eco
  • ids_attack.c / .h — Génération d'attaques RPL simulées
  • ids_campaign_log.c / .h — Log structuré pour le pipeline d'analyse

2. Niveau 1 : Nœuds membres

Chaque nœud membre (non-CH) exécute les tâches suivantes :

  • Surveillance locale du trafic entrant et sortant
  • Application des 4 règles de détection (R1-R4)
  • Calcul du score d'anomalie local (LAS, Eq. 4)
  • Transmission périodique du LAS au Cluster Head
  • Participation au processus d'élection du CH

3. Niveau 2 : Cluster Heads (CH)

Les Cluster Heads ont des responsabilités supplémentaires :

  • Collecte des LAS provenant des membres du cluster
  • Agrégation et confirmation croisée des anomalies
  • Prise de décision consolidée (alerte confirmée ou rejetée)
  • Génération d'alertes vers la racine RPL (sink)
  • Gestion du re-clustering et rotation du rôle CH

4. Communication entre niveaux

Les échanges suivants structurent la communication :

  1. Phase de formation : messages de découverte, calcul d'affinité, attribution des membres aux CH
  2. Phase d'élection :广播 des valeurs de fitness, vote, annonce du nouveau CH
  3. Phase de monitoring : rapports LAS périodiques des membres vers le CH
  4. Phase d'alerte : décision CH → message d'alerte vers la racine
  5. Phase de re-clustering : déclenché périodiquement ou si la qualité du cluster se dégrade (Eq. 2)

5. Fichier de coordination : clusterids-node.c

Le fichier clusterids-node.c est le point d'entrée du firmware. Il initialise la pile RPL, configure le trafic UDP selon 4 classes (C0-C3), démarre le module IDS selon le variant choisi, et orchestre les phases de clustering et de détection. La racine RPL (DAG root) joue un rôle particulier : elle reçoit les alertes des CH et peut déclencher des actions de mitigation.

Note : L'architecture est conçue pour minimiser l'overhead de communication. Les rapports LAS sont compressés et envoyés périodiquement, pas à chaque paquet. Les CH n'agrègent que les scores dépassant un seuil configurable.
