Agrégation au niveau Cluster Head

Cours 06 — Module IDS-IOT / RPL-ClusterIDS
  • Auteur : Dr. Madani BELACEL
  • Code source : ids_ch.c / ids_ch.h

1. Rôle de l'agrégation CH

Le Cluster Head (CH) reçoit les LAS périodiques de tous les membres de son cluster. L'agrégation au niveau CH est cruciale pour :

  • Réduire les faux positifs (un seul nœud qui signale une anomalie peut être erroné)
  • Corroborer les anomalies par confirmation croisée entre plusieurs membres
  • Produire une décision consolidée avant d'alerter la racine RPL
  • Maintenir une vue d'ensemble de l'état de sécurité du cluster

2. Collecte des LAS

Le CH maintient une table las_table[member_id] qui stocke les derniers LAS reçus de chaque membre. Les LAS sont timestampés pour détecter les absences de rapport (silence prolongé pouvant indiquer un nœud compromis).

Le CH attend les rapports pendant une fenêtre T_collect (par défaut 30 secondes simulées). Passé ce délai, il procède à l'agrégation sur les données disponibles.

3. Agrégation pondérée

Le CH calcule un score agrégé AggLAS pour chaque nœud cible k (le nœud suspecté) :

AggLAS(k) = (1/N_k) · Σ_{m ∈ M_k} LAS(m → k) · w_trust(m)

Où :

  • N_k — Nombre de membres ayant rapporté un LAS sur k
  • M_k — Ensemble des membres ayant surveillé k
  • w_trust(m) — Poids de confiance du membre m (basé sur l'historique de fiabilité)

4. Cross-confirmation

La cross-confirmation est le mécanisme clé pour réduire les faux positifs. Une anomalie est confirmée seulement si :

  • Au moins k_min membres (par défaut 2) ont rapporté un LAS > θ_las pour le même nœud cible
  • OU un seul membre rapporte un LAS > θ_las_high (seuil haut, par défaut 0.8)
  • Le CH lui-même observe une anomalie directe (monitoring passif)

5. Décision CH et génération d'alerte

Si l'agrégation confirme l'anomalie, le CH génère un message d'alerte contenant :

  • ID du nœud suspect
  • Type d'attaque probable (déduit des règles R1-R4 dominantes)
  • Score agrégé AggLAS
  • Timestamp et durée de l'observation
  • Liste des membres témoins

L'alerte est envoyée à la racine RPL (sink) via le protocole de routage standard.

6. Réduction des faux positifs

L'efficacité de la cross-confirmation est mesurée par le taux de réduction des faux positifs (FPR Reduction). Les résultats préliminaires montrent une réduction de 40-60% du FPR par rapport à une détection locale sans agrégation.

ConfigurationFPR (détection locale)FPR (après agrégation CH)Réduction
Full mode12.3%5.1%58.5%
Balanced mode15.7%7.2%54.1%
Eco mode18.9%9.8%48.1%

7. Implémentation dans ids_ch.c

Fonctions principales : collect_las(), aggregate_las(), cross_confirm(), generate_alert(). La table des LAS est une structure statique pour minimiser l'utilisation mémoire.

Note : Le CH peut également détecter les nœuds qui ne rapportent jamais de LAS (comportement suspect) via le mécanisme de silence detection implémenté dans check_absence().
