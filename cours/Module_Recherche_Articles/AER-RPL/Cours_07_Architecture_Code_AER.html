Cours 07 : Architecture détaillée du code

Cours 07 — Architecture détaillée du code
  • Auteur : Dr. Madani BELACEL
  • Durée estimée : 1h30
  • Objectifs : Comprendre l'architecture du code source de RPL-AER et l'interaction entre les modules

1. Structure du dépôt RPL-AER

Le dépôt RPL-AER est structuré comme une application Contiki-NG :

RPL-AER/
  examples/rpl-aer/
    rpl-aer.c          -- Logique principale
    rpl-aer.h          -- Déclarations
    rpl-aer-sink.c     -- Nœud puits
    udp-client.c       -- Client UDP
    udp-server.c       -- Serveur UDP
    mcs_calculator.c/h -- Calcul MCS
    lstm_predictor.c/h -- Prédiction LSTM

    attack_detector.c/h-- Détection attaques

  tools/

    simulate_results.py
    generate_csc.py
  simulation/

Objectifs pédagogiques
  • Comprendre l'architecture modulaire du code RPL-AER
  • Analyser le rôle de chaque fichier source
  • Étudier les interactions entre les modules
  • Maîtriser la configuration via project-conf.h

2. rpl-aer.c — Logique principale

Ce fichier est le cœur du protocole (332 lignes). Il gère :

  • L'initialisation du contexte (rpl_aer_init(), ligne 321)
  • Le calcul périodique du MCS via des timers (ctimer, lignes 239-263)
  • La mise à jour de l'énergie et la simulation solaire
  • La détection d'attaques
  • Les logs de performance (PDR, latence, throughput, lignes 276-293)

3. Le processus d'initialisation

La fonction rpl_aer_init() (rpl-aer.c:321-332) :

1 void rpl_aer_init(void) { 2 rpl_aer_context_init(); 3 rpl_aer_performance_init(); 4 ctimer_set(&mcs_timer, RPL_AER_MCS_UPDATE_INTERVAL, mcs_update_callback, NULL); 5 ctimer_set(&energy_timer, RPL_AER_ENERGY_UPDATE_INTERVAL, energy_update_callback, NULL); 6 ctimer_set(&security_timer, RPL_AER_SECURITY_UPDATE_INTERVAL, security_update_callback, NULL); 7 ctimer_set(&performance_timer, RPL_AER_PERFORMANCE_UPDATE_INTERVAL, performance_update_callback, NULL); 8 LOG_INFO("RPL-AER: Protocol initialized successfully\n"); 9 }

4. Interaction entre les modules

  • rpl-aer.c appelle mcs_calculator_compute() via mcs_calculator.h
  • mcs_calculator sollicite harvest_module pour l'ECS, lstm_predictor pour le PEC
  • trust_module surveille les voisins et ajuste le MCS via un facteur de confiance
  • attack_detector analyse les logs RSSI et les taux d'ACK
  • Le sink collecte les métriques via la structure partagée rpl_aer_context_t

5. Configuration dans project-conf.h

Les paramètres ajustables sont centralisés :

1 #define RPL_AER_MCS_ALPHA 0.5 2 #define RPL_AER_MCS_BETA 0.3 3 #define RPL_AER_MCS_GAMMA 0.2 4 #define RPL_AER_LSTM_WINDOW 5 5 #define RPL_AER_TRUST_ENABLED 1 6 #define RPL_AER_HARVEST_ENABLED 1 7 #define RPL_AER_MOBILITY_ENABLED 1

6. Les timers périodiques

Timer Intervalle Callback Action
mcs_timer10 secondesmcs_update_callbackRecalcule MCS et log
energy_timer5 secondesenergy_update_callbackMet à jour énergie et log
security_timer2 secondessecurity_update_callbackDétection d'attaques et log
performance_timer30 secondesperformance_update_callbackPDR, latence, throughput
Questions de réflexion
  1. Pourquoi le timer de sécurité est-il le plus fréquent (2s) ?
  2. Comment les quatre timers interagissent-ils dans le processus ?
  3. Que se passe-t-il si le MCS n'est jamais recalculé ?
  4. Quel est l'avantage d'avoir des timers séparés plutôt qu'un seul ?
  5. Proposer un nouvel intervalle pour le timer MCS et justifier.
