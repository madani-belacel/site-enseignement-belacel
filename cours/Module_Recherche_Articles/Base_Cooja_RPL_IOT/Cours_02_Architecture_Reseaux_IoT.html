Cours 02 — Architecture des Réseaux IoT

Cours 02 — Durée estimée : 2h30 — Protocoles et standards IoT

1. La pile protocolaire IoT

Contrairement aux réseaux TCP/IP classiques, l'IoT nécessite une pile protocolaire adaptée aux contraintes des objets contraints (mémoire, énergie, puissance de calcul). La pile typique se compose de :

  • Couche physique/MAC : IEEE 802.15.4
  • Couche adaptation : 6LoWPAN
  • Couche réseau : IPv6, RPL
  • Couche transport : UDP (principalement)
  • Couche application : CoAP, MQTT

2. IEEE 802.15.4 — Physique et MAC

IEEE 802.15.4 est le standard de référence pour les réseaux personnels sans fil à faible débit (LR-WPAN). C'est la couche la plus utilisée dans les WSN.

Caractéristiques PHY :

  • Bandes de fréquence : 868 MHz (Europe), 915 MHz (Amérique), 2.4 GHz (monde)
  • Débit : 20-250 kbps selon la bande
  • Portée : 10-100 mètres
  • Puissance d'émission : ~1 mW (très faible)

Caractéristiques MAC :

  • CSMA/CA (Carrier Sense Multiple Access with Collision Avoidance)
  • Trames de 127 octets maximum (très petite taille)
  • Deux modes : beacon-enabled (synchronisé) et non-beacon (asynchrone)
  • Topologies : étoile, arbre, maillage (via couche supérieure)

3. 6LoWPAN — IPv6 sur LoWPAN

6LoWPAN (IPv6 over Low-Power Wireless Personal Area Networks) est défini par la RFC 4944. Il joue le rôle de couche d'adaptation entre IEEE 802.15.4 et IPv6.

Problèmes résolus :

  • Taille des trames : IPv6 requiert 1280 octets MTU minimum, mais 802.15.4 ne supporte que 127 octets → fragmentation et réassemblage
  • En-tête IPv6 : 40 octets, trop lourd → compression d'en-tête (HC1, HC2, IPHC)
  • Adressage : mappe les adresses MAC 64-bit en adresses IPv6

Compression d'en-tête (IPHC) : réduit l'en-tête IPv6 de 40 octets à 2-12 octets. Les champs redondants (version, traffic class, flow label) sont éliminés ou inférés.

4. UDP et TCP pour l'IoT

UDP (User Datagram Protocol) est le protocole de transport privilégié dans l'IoT pour plusieurs raisons :

  • Faible overhead (8 octets d'en-tête contre 20 pour TCP)
  • Pas de connexion à établir (évite le handshake TCP)
  • Pas de contrôle de congestion (simplicité)
  • La fiabilité est déléguée à la couche application si nécessaire

TCP est rarement utilisé dans les réseaux de capteurs car le handshake et le contrôle de congestion consomment trop d'énergie et de bande passante.

5. CoAP — Constrained Application Protocol

CoAP (RFC 7252) est un protocole applicatif conçu pour les nœuds contraints. Il s'inspire de REST/HTTP mais avec un overhead minimal.

Caractéristiques :

  • Transport sur UDP (port 5683)
  • Modèle requête/réponse avec 4 méthodes : GET, POST, PUT, DELETE
  • Observation (observe) pour les notifications push
  • Découverte de ressources via /.well-known/core
  • Fiabilité optionnelle via messages confirmables (CON) et non-confirmables (NON)

6. Pile protocolaire complète dans Contiki-NG

Dans Contiki-NG, la pile réseau est implémentée dans le répertoire os/net/ :

os/net/
  mac/       — Contrôle d'accès au médium (CSMA, TSCH)
  llsec/     — Sécurité de liaison
  ipv6/      — IPv6, ICMPv6, RPL
  ipv6/uip-udp.c    — UDP
  ipv6/uip-tcp.c    — TCP (optionnel)
  app-layer/ — CoAP (er-coap)

7. Résumé

Ce cours a présenté la pile protocolaire IoT de la couche physique jusqu'à l'application. IEEE 802.15.4 fournit la base radio, 6LoWPAN adapte IPv6 aux trames de petite taille, UDP offre un transport léger, et CoAP permet des échanges RESTful optimisés. Cette architecture est implémentée dans Contiki-NG et simulée avec Cooja.
