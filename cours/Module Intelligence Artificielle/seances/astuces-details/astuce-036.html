🔍 Astuce 36 — Demander d'expliquer un code avant de le modifier

Explication détaillée · Module Intelligence Artificielle — 2e année PEP

1. Le texte source

Dans Cursor ou OpenCode : demande d'abord le plan (« montre-moi les fichiers que tu vas toucher et pourquoi »). Valide le plan, puis lance l'écriture.

36 Demander d'expliquer un code avant de le modifier

Pourquoi ça marche

Forcer l'IA à expliquer un bloc de code permet de vérifier qu'elle a bien compris son fonctionnement avant d'introduire des régressions.

Étapes

  1. Soumets le code existant à l'assistant.
  2. Demande une explication détaillée ligne par ligne ou par bloc logique.
  3. Valide l'explication avant de demander des modifications.

Prompt à copier

Explique-moi en détail ce que fait ce code, ligne par ligne, avant que nous ne commencions à y apporter des modifications : [insérer le code].

Exemple réel

Comprendre un script écrit par un tiers avant d'y intégrer une nouvelle règle.

Erreur fréquente

Modifier un code existant sans en comprendre la logique sous-jacente, en faisant confiance aveuglément à l'IA.

Vérification

  • ☐ Le code a été expliqué par l'IA.
  • ☐ L'explication correspond à la réalité technique.
  • ☐ Les impacts potentiels des modifications ont été identifiés.

Variante (Anglais / Français)

Anglais : Ask the AI to explain the code before modifying it. Français : Demande à l'IA d'expliquer le code avant de le modifier.

2. Explication phrase par phrase

« Demande d'abord le plan » → Avant que l'agent modifie le moindre fichier, tu lui demandes de te dire ce qu'il compte faire. C'est une étape où rien n'est encore écrit sur le disque.

« Montre-moi les fichiers que tu vas toucher » → Tu exiges la liste précise des fichiers concernés. Si la liste est trop longue, tu peux arrêter et réduire le périmètre. C'est ton garde-fou contre les modifications massives.

« Et pourquoi » → Tu obliges l'agent à justifier chaque action. Cela révèle les faux pas : « je vais modifier config.py pour changer le port » — mais tu ne voulais pas toucher au port.

« Valide le plan, puis lance l'écriture » → Tu sépares les deux moments : réfléchir, puis exécuter. Tu ne mélanges jamais les deux, sinon tu perds le contrôle.

3. Une analogie pour comprendre

Imagine que tu fais construire une maison.

Sans plan : tu dis à l'ouvrier « construis-moi une maison ». Il commence par les fondations, mais il a oublié la salle de bain, il met la cuisine au premier étage, il n'y a pas de fenêtres au sud. À la fin, il faut tout casser.

Avec plan : tu dis « montre-moi les plans ». L'ouvrier te présente les 4 pièces, leur emplacement, l'orientation des fenêtres. Tu vois une erreur : la cuisine au premier étage. Tu la signales. Il corrige le plan. Puis il construit.

Les agents IA fonctionnent pareil. Le mode Plan évite de casser 8 fichiers pour un résultat qui ne te convient pas.

4. Les composants décomposés

Élément du planCe que ça te ditCe que tu vérifies
Liste des fichiersOù l'agent va écrireAucun fichier sensible ? Aucun fichier inutile ?
Raison de chaque actionLe « pourquoi » derrière chaque modificationLa raison correspond-elle à ton besoin ?
Ordre des étapesCe qui se fait avant quoiY a-t-il un risque de casser avant de créer ?
EstimationCombien de fichiers, combien de tempsEst-ce proportionné à ta demande ?

5. Application pratique — ajouter une fonctionnalité à un site

Sans mode Plan :

Ajoute un formulaire de contact à mon site.

L'agent modifie index.html, crée contact.php, ajoute du CSS dans style.css, modifie main.js, touche au config.php pour ajouter une adresse e-mail, et — au passage — renomme une variable dans 3 autres fichiers. Tu ne sais plus ce qui a changé, ni pourquoi.

Avec mode Plan :

Demande : ajouter un formulaire de contact à mon site. AVANT TOUTE ÉCRITURE : donne-moi le plan. Format attendu : - Fichiers à créer - Fichiers à modifier - Raison pour chacun - Estimation (temps, risque)

L'agent te renvoie :

  • Créer contact.html (page de contact)
  • Modifier index.html (ajout du lien vers la page)
  • Ajouter CSS dans style.css (nouvelle section)
  • Ne touche à aucun fichier PHP ou JS pour le moment.

Tu valides. Il écrit. Tu vérifies. 4 fichiers annoncés, 4 fichiers modifiés — pas de surprise.

6. Le réflexe à retenir

Plan d'abord, écriture ensuite. Jamais les deux en même temps.

La règle à appliquer à chaque nouvelle tâche : quand tu demandes quelque chose à un agent, termine toujours ton prompt par :

Donne-moi d'abord le plan. J'attends ma validation avant que tu écrives.

Cette phrase seule transforme un agent imprévisible en collaborateur fiable.

7. Erreurs fréquentes à éviter

  1. Valider le plan sans le lire. Le plan n'a de valeur que si tu le lis. 30 secondes de lecture économisent 30 minutes de correction.
  2. Accepter un plan trop large. Si l'agent annonce 15 fichiers modifiés, réduis. « Commence par les 3 premiers, montre-moi le résultat, on continue après. »
  3. Modifier le plan au fur et à mesure. Si tu changes d'avis en cours d'exécution, arrête l'agent et refais un plan propre.
  4. Utiliser le mode Plan pour tout. Pour une modification d'une ligne, pas besoin. Réserve le Plan aux tâches qui touchent 2 fichiers ou plus.
  5. Ne pas sauvegarder avant. Même avec un plan validé, garde une copie (ou un git init) pour pouvoir revenir en arrière.

9. Ce que tu dois retenir

  • Plan avant écriture. La phrase magique : « Donne-moi d'abord le plan. »
  • Lire le plan. Vérifier les fichiers, les raisons, l'ordre.
  • Réduire si trop large. 3 fichiers par étape, pas 15.
  • Sauvegarder avant. Un plan ne remplace pas un filet de sécurité.
